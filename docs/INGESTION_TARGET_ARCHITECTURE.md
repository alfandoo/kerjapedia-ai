# KerjaPedia AI Target Ingestion Architecture

**Status:** Proposed architecture; not implemented
**Date:** 2026-09-13
**Based on:** `docs/INGESTION_AUDIT.md` and the current repository implementation
**Scope:** Ingestion, ingestion persistence, release-candidate indexing, and ingestion validation
**Explicitly out of scope:** Retrieval implementation changes

## Executive summary

KerjaPedia AI should evolve the active `app.services.ingestion` pipeline rather than introduce a third ingestion implementation. The target keeps the strongest parts of the current system—PostgreSQL governance, immutable artifacts, Celery execution, explicit human review, and immutable Pinecone release namespaces—while introducing stronger stage boundaries, normalized internal models, exact provenance, safe re-ingestion, and verified indexing.

The design deliberately does not require a workflow platform, event bus, distributed transaction coordinator, or new vector database. One orchestrator coordinates deterministic modules. PostgreSQL remains the system of record, the artifact store retains large intermediate representations, Celery provides durable execution, and Pinecone remains the production vector index.

The key architectural rule is that each stage consumes a versioned immutable model and returns another versioned immutable model plus typed diagnostics. Parsing does not know about embeddings. Chunking does not know about persistence. Indexing cannot publish directly. Publication remains an explicit governance action that activates a fully verified release namespace.

## Design goals

1. Parse Indonesian legal PDFs with page, layout, OCR, table, and source-span provenance.
2. Represent Indonesian legal hierarchy without flattening Bagian, Paragraf, Ayat, Huruf, or Angka.
3. Produce deterministic chunks and metadata from explicit, versioned inputs.
4. Make every chunk traceable to the exact pages and source character spans that produced it.
5. Make re-ingestion idempotent and distinguish content versions, builds, and execution attempts.
6. Allow failed work to resume only when stage inputs and outputs are demonstrably compatible.
7. Produce actionable, durable diagnostics rather than generic exception names.
8. Verify the complete vector release before it can become active.
9. Keep each stage independently testable.
10. Preserve current retrieval behavior and Pinecone metadata compatibility during migration.

## Non-goals

- Replacing PostgreSQL, Celery/Redis, Pinecone, Supabase Storage, or the current governance workflow.
- Adding DOCX, HTML, or web crawling in the first implementation. The loader contract allows them later, but only PDF is enabled initially.
- Moving retrieval, answer generation, prompt management, or reranking into the ingestion package.
- Automatically inferring legal validity or supersession without source verification and legal review.
- Silently correcting uncertain OCR output, article numbers, monetary values, or dates.
- Rewriting or mutating existing v2 ingestion artifacts and active releases.

## Architectural decisions

### One authoritative ingestion namespace

`apps/api/app/services/ingestion` remains the authoritative ingestion namespace. Capabilities from the currently unwired `app.services.rag` package may be ported only after their behavior is covered by tests and mapped to the normalized contracts in this document. The target does not connect both pipelines together or place a new pipeline beside them.

### Internal models are separate from transport and persistence

- Internal domain objects use frozen dataclasses, enums, tuples, and explicit schema versions.
- FastAPI request/response validation remains in Pydantic API schemas.
- SQLAlchemy models remain persistence adapters rather than domain objects.
- Pinecone payloads are generated by an indexing adapter from finalized chunk metadata.

This prevents database or provider concerns from leaking into parsing and chunking.

### Immutable stage outputs

Every stage output has:

- a schema version;
- a deterministic input fingerprint;
- a deterministic artifact checksum;
- typed diagnostics;
- an immutable artifact representation.

A later stage never edits an earlier stage's output. Corrections create a new build or a new reviewed disposition.

### Staging before publication

Embedding and indexing do not make knowledge available to users. Vectors are written into a release-specific staging namespace, reconciled against an index manifest, evaluated, approved, and only then activated through the existing release lifecycle.

## Normalized internal models

### Common rules

- Models are frozen and use tuples instead of mutable lists where practical.
- Every serialized top-level model includes `schema_version`.
- Dates are timezone-aware UTC ISO-8601 values.
- Checksums are lowercase full SHA-256 strings.
- Optional fields mean “not available”; they do not use placeholder values such as `0`, `unknown`, or empty strings when absence matters.
- Enums define stage, severity, retryability, page disposition, extraction mode, legal node type, normative role, and lifecycle status.

### Identity models

#### `DocumentIdentity`

Represents stable legal identity, independent of file bytes:

- `document_id`: human-readable stable key, for example `UU-13-2003`.
- `regulation_type`.
- `number`.
- `year`.
- `issuer`.
- `jurisdiction`, defaulting to `ID`.
- `identity_schema_version`.

An uploaded filename may suggest identity but cannot establish it. Ambiguous uploads remain pending until an administrator confirms the legal identity.

#### `DocumentVersionIdentity`

Represents observed source bytes:

- `version_id`.
- `document_id`.
- full `source_sha256`.
- `size_bytes`.
- `source_origin`.
- `source_reference` and canonical source URL.
- `observed_at`.

Different bytes always produce different versions. The human-facing legacy integer version may remain as a compatibility field but is no longer authoritative identity.

#### `BuildIdentity`

Represents one deterministic transformation definition:

- `build_id`.
- `version_id`.
- `metadata_sha256`.
- `pipeline_fingerprint`.
- `code_revision` or container image digest.
- domain/artifact schema versions.
- parser, cleaner, chunker, OCR, and evaluation versions.
- complete stage configuration hash.
- embedding vector-space ID.

The build digest is calculated from canonical serialization of all these inputs. Runtime provenance is persisted; any runtime attribute that can change deterministic output is included in the fingerprint.

#### `IngestionRun`

Represents one execution attempt:

- unique random `run_id`/job ID.
- deterministic `idempotency_key`.
- `build_id`.
- mode: `reuse`, `resume`, `recompute`, or `shadow`.
- attempt number.
- current stage and status.
- queued, started, heartbeat, and completed timestamps.
- terminal diagnostic summary.

Build identity and execution identity are deliberately separate. Forced recomputation creates a new run without inventing a new build fingerprint.

### Source and validation models

#### `SourceDocument`

- Source origin: curated, upload, or connector.
- Source registry ID and reference.
- Canonical URL and local immutable artifact reference.
- Media type and filename.
- Size and full checksum.
- Proposed document metadata.
- Collection time and source verification state.

#### `ValidationReport`

- Eligibility and quarantine state.
- Detected media type and PDF version.
- File structure validity.
- Encrypted/password-required state.
- Page count and page-load failures.
- Configured byte/page/resource-limit results.
- Duplicate version candidates.
- Typed diagnostics.

Expected invalid input produces an ineligible or quarantined report; it is not represented only by a generic exception.

### Page-level models

#### `SourceSpan`

- `page_number`.
- raw-text start/end offsets.
- extracted-text start/end offsets.
- normalized-text start/end offsets.
- optional PDF bounding box.
- source block/line identifier.

Ranges use zero-based, half-open offsets. Source maps are preserved through cleaning, segment construction, merging, and chunk splitting.

#### `TableBlock`

- Stable table ID.
- Page and bounding box.
- Ordered rows and normalized cells.
- Text serialization used for parsing/chunking.
- Extraction method and confidence.
- Source spans and diagnostics.

#### `Page`

- Page number and printed-page label when detectable.
- Raw and extracted text.
- Normalized text after cleaning.
- Layout mode: linear, columns, table-heavy, mixed, scanned, or empty.
- Extraction method and OCR provenance.
- Rotation, blocks, tables, and source mappings.
- Before/after quality metrics.
- Final disposition.
- Diagnostics.

#### `PageDocument`

- Document/version/build references.
- Ordered immutable pages.
- Parser/OCR/cleaner configuration.
- Page counts by disposition.
- Document-level extraction diagnostics.

Every page must finish in one of these dispositions:

- `text_extracted`;
- `ocr_extracted`;
- `intentionally_empty`;
- `non_substantive_reviewed`;
- `blocked`.

An undispositioned or blocked substantive page prevents release.

### Legal structure models

#### `LegalNodeType`

The initial taxonomy is:

```text
DOCUMENT
├── OPENING
│   ├── MENIMBANG
│   ├── MENGINGAT
│   └── MEMUTUSKAN
├── BAB
│   ├── BAGIAN
│   │   ├── PARAGRAF
│   │   │   ├── PASAL
│   │   │   │   ├── AYAT
│   │   │   │   │   ├── HURUF
│   │   │   │   │   │   └── ANGKA
├── EXPLANATION
└── ATTACHMENT
    ├── TABLE
    └── UNSTRUCTURED
```

`Ketentuan Umum`, `Ketentuan Peralihan`, and `Ketentuan Penutup` are represented as BAB nodes with normalized semantic roles in addition to their printed titles.

#### `LegalSection`

- Stable node ID.
- Node type and normalized semantic role.
- Raw marker, normalized label, and optional heading title.
- Parent node ID, ordered path, and sibling order.
- Full normalized text and text checksum.
- Exact source spans.
- Marker provenance and parse confidence.
- Local diagnostics.

#### `StructuredLegalDocument`

- Page-document reference.
- Root node ID.
- Ordered node collection and ID index.
- Hierarchy schema/parser version.
- Structure validation report.

The parser recovers locally. A malformed Ayat records a diagnostic on that node/page; it must not cause all subsequent content to inherit an incorrect parent silently.

### Chunk and metadata models

#### `ChunkMetadata`

- Metadata schema version.
- Document, version, build, and legal-node IDs.
- Regulation type, number, year, issuer, jurisdiction, title, and short title.
- Distinct BAB, Bagian, Paragraf, Pasal, Ayat, Huruf, and Angka labels.
- Legal path and normative role.
- Parent and sibling node/chunk IDs.
- Chunk part number and total parts.
- Exact source spans and source/printed page labels.
- Source URL, source checksum, and source verification state.
- Legal status, publication status, effective dates, and document relationship snapshot.
- Topics, language, OCR provenance, and quality indicators.
- Body, retrieval-text, and metadata checksums.

Metadata generation is deterministic: it receives a complete context object and performs no database, clock, network, or environment lookup.

#### `Chunk`

- Content-derived stable chunk ID.
- Legal node ID.
- Body text.
- Retrieval text.
- Actual BGE tokenizer count for the final retrieval text.
- Part/continuation information.
- `ChunkMetadata`.

It contains no embedding vector, SQLAlchemy model, artifact path, or Pinecone client state.

Chunk IDs are derived from document version, legal node identity, ordered source spans, part number, and normalized body checksum. Identical deterministic rebuilds therefore retain IDs; changes to relevant content or provenance change the ID.

### Embedding and index models

#### `EmbeddingRecord`

- Chunk ID and retrieval-text checksum.
- Dense vector and sparse vector.
- Sparse kind: native, lexical, or none.
- Provider, model, pinned revision, vector-space ID, and dimensions.
- Vector norm and validation status.
- Run, batch, and attempt identifiers.
- Provider request ID, latency, token count, and estimated cost where applicable.
- Typed diagnostics.

#### `IndexManifest`

- Index and staging namespace.
- Release and build IDs.
- Vector-space ID.
- Sorted expected vector IDs and their aggregate checksum.
- Expected, acknowledged, and verified counts.
- Metadata schema/version and aggregate metadata checksum.
- Verification results and creation provenance.

#### `IngestionValidationReport`

- Versioned metrics for every stage.
- Blocking, advisory, and waived-with-review findings.
- Page, hierarchy, chunk, embedding, and index coverage.
- Deterministic retrieval probe results.
- Publish recommendation and reasons.

#### `IngestionResult`

- Run/build/version identities.
- Terminal status.
- Stage and artifact manifests.
- Diagnostics.
- Validation report.
- Optional release-candidate reference.

## Typed diagnostics

All stages return `StageDiagnostic` records with:

- stable diagnostic code;
- severity: info, warning, error, or critical;
- stage;
- retryability: retryable, permanent, or review-required;
- safe human-readable message;
- document/page/node/chunk/batch context;
- evidence artifact reference;
- recommended operator action.

Examples include `pdf.password_required`, `pdf.page_load_failed`, `ocr.quality_not_improved`, `structure.ayat_gap`, `chunk.token_limit_exceeded`, `embedding.rate_limited`, and `index.vector_missing`.

Provider or programming exceptions may still be raised, but the orchestrator must persist a sanitized diagnostic and failure stage before completing the run as failed.

## Stage behavior and exit criteria

### 1. Source loading

- Load curated or uploaded bytes using a safe loader.
- Never derive canonical legal identity solely from a filename.
- Produce a source receipt with checksum, size, origin, and immutable artifact reference.

**Exit:** Source bytes are readable and have a stable receipt.

### 2. Validation and identity

- Validate PDF signature and structure, encryption, page loading, limits, and declared metadata.
- Find checksum/legal-identity duplicate candidates.
- Resolve document, version, build, run, and idempotency identities.

**Exit:** The source is eligible, or it is durably quarantined with actionable reasons.

### 3. PDF parsing and selective OCR

- Extract blocks with coordinates and reconstruct reading order.
- Detect linear, multi-column, table-heavy, mixed, scanned, and empty pages.
- Extract tables as cells plus a deterministic textual representation.
- OCR only pages selected by quality rules.
- Preserve both original and OCR-derived text and measure quality improvement.

**Exit:** Every page has content, a valid reviewed disposition, or a blocking diagnostic.

### 4. Cleaning and normalization

- Apply Unicode normalization, safe-control removal, whitespace normalization, margin removal, line reflow, and conservative dehyphenation.
- Track each removal/transformation and maintain source mappings.
- Never silently repair uncertain legal numbers or values.

**Exit:** Every normalized character used downstream maps to source evidence.

### 5. Legal structure

- Detect Indonesian legal markers and construct the explicit hierarchy.
- Preserve raw markers, printed labels, semantic roles, source spans, and confidence.
- Validate ordering, numbering, nesting, and parser state transitions.

**Exit:** The tree is internally valid or all anomalies have blocking/review dispositions.

### 6. Chunking and metadata

- Start with legal leaf nodes and merge only within an allowed legal boundary.
- Split oversized leaves at lower legal markers or sentence boundaries.
- Use the pinned BGE tokenizer on final retrieval text.
- Use sentence overlap only for continuations of one oversized node.
- Generate complete deterministic provenance metadata.

**Exit:** Every chunk is non-empty, within the hard token limit, stable, and exactly traceable.

### 7. Deduplication

- Remove exact duplicate chunks within one version deterministically.
- Block accidental duplicate source versions unless an explicit canonical/alias disposition exists.
- Flag near duplicates and cross-document duplicates for review; do not silently remove legal text.

**Exit:** No undispositioned exact duplicate remains.

### 8. Embedding

- Embed in bounded batches with provider-specific timeouts and retry classification.
- Checkpoint a batch only after every vector in it is validated.
- Validate input checksum, vector space, dimensions, finite values, normalization, and native sparse requirements.

**Exit:** There is exactly one valid embedding record for each accepted chunk.

### 9. Staging index and verification

- Write only to a unique immutable staging namespace.
- Record acknowledged counts without assuming success when the provider response is incomplete.
- Fetch expected IDs in batches and verify dimensions and metadata checksums.
- Reconcile expected, acknowledged, stored, and verified counts.

**Exit:** The complete index manifest is verified. Partial namespaces are failed and ineligible.

### 10. Validation and publication

- Apply one gate policy shared by ingestion, review, and release building.
- Run page, structure, chunk, metadata, embedding, indexing, and retrieval probes.
- Require source verification, legal review, build approval, and zero unresolved blocking gates.
- Activate the verified namespace through the existing release lifecycle.

**Exit:** The release is active, or remains inactive with explicit reasons. The previous release remains rollback-capable.

## Idempotency and safe re-ingestion

### Identity rules

- Same legal identity, same bytes: same document version.
- Same legal identity, new bytes: new document version.
- Same version, changed canonical metadata: new build.
- Same version/metadata, changed stage config, code, schema, or vector space: new build.
- Same complete build fingerprint: same build.
- Every execution attempt has a distinct run ID.

### Normal execution

If a successful matching build and its complete artifact manifest verify correctly, ingestion returns that build without recomputation.

### Resume

A stage can be resumed only when:

- its recorded input fingerprint equals the current input fingerprint;
- its output schema is supported;
- every output checksum verifies;
- all required output records exist;
- the stage was completed atomically.

Otherwise that stage and all downstream stages are recomputed.

### Forced recomputation

`force_recompute` creates a new run, ignores prior stage checkpoints, writes temporary artifacts, and compares the result with the existing deterministic build. Matching output confirms reproducibility. Different output becomes a blocking `build.nondeterministic_output` diagnostic unless the build fingerprint was incomplete, in which case the fingerprint defect must be corrected and a new build created.

### Failure semantics

- Permanent source failures are quarantined, not retried.
- Retryable provider/infrastructure failures use bounded exponential backoff with jitter and provider `Retry-After` instructions.
- A failed stage persists diagnostics before the run terminates.
- Temporary artifacts are never treated as complete build artifacts.
- Database completion follows artifact promotion.
- Pinecone indexing follows canonical build completion.
- A failed namespace cannot be validated or activated.
- A retention job removes expired failed/staging namespaces and abandoned temporary artifacts.

## Database changes

All database changes are additive during migration.

### `document_versions`

Add:

- `metadata_sha256`;
- `identity_schema_version`;
- `source_origin`;
- `source_reference`;
- `duplicate_disposition`;
- nullable `canonical_version_id` self-reference.

Retain current `version`, `sha256`, URLs, governance state, publication state, and artifact paths. The existing integer version remains a compatibility value; `version_id` plus full SHA-256 is authoritative.

### `ingestion_builds`

Add:

- `pipeline_fingerprint`;
- `code_revision`;
- `domain_schema_version`;
- `stage_manifest` JSONB;
- `failure_stage`;
- `failure_code`;
- `diagnostics` JSONB.

Update the unique build fingerprint to include the complete target identity rather than only version/config/model fields.

### `ingestion_jobs`

Change semantics from a deterministic build-derived job ID to one execution attempt:

- random job/run ID;
- deterministic indexed `idempotency_key`;
- attempt number;
- run mode;
- current stage;
- structured diagnostics;
- queued, started, heartbeat, and completed timestamps.

Existing response fields remain available.

### `legal_nodes`

Add a new table containing:

- node ID, build/version/document IDs;
- parent node ID;
- node type and semantic role;
- normalized label/title;
- sibling order and ordered path;
- page range and exact source spans JSONB;
- normalized text and checksum;
- confidence and diagnostics JSONB.

Page content itself remains in immutable artifacts to avoid duplicating large extraction payloads in PostgreSQL.

### `chunks`

Add:

- legal node ID;
- chunk ordinal, part, and total parts;
- metadata schema version;
- source spans JSONB;
- body checksum;
- retrieval-text checksum;
- metadata checksum.

Continue populating legacy chapter, section, article, paragraph, and page fields during transition.

### `chunk_embeddings`

Add:

- vector-space ID;
- embedding run and batch IDs;
- sparse kind;
- provider request/attempt metadata where applicable.

Dense and sparse vectors may remain JSONB because PostgreSQL is the system of record and Pinecone remains the production similarity index. This architecture does not introduce pgvector retrieval.

### `rag_index_releases`

Add:

- staging namespace;
- index manifest checksum;
- expected, acknowledged, and verified vector counts;
- vector ID aggregate checksum;
- index verification report JSONB.

## Artifact architecture

New artifacts use a v3 schema alongside existing v2 paths:

```text
storage/ingestion-v3/
└── documents/<document_id>/versions/<version_id>/
    ├── source/
    │   └── source.pdf
    └── builds/<build_id>/
        ├── runs/<run_id>/
        │   └── diagnostics.jsonl
        ├── stages/
        │   ├── validation.json
        │   ├── pages.raw.json
        │   ├── pages.ocr.json
        │   ├── pages.cleaned.json
        │   ├── legal-document.json
        │   ├── chunks.json
        │   ├── deduplication.json
        │   ├── embeddings.jsonl
        │   ├── index-manifest.json
        │   └── validation-report.json
        └── build-manifest.json
```

The final build manifest is written last and references every stage artifact by schema, input fingerprint, checksum, and size. Existing v2 artifacts are never rewritten.

## Backward compatibility

### API compatibility

- Preserve existing ingestion endpoints and current response fields.
- Add run ID, current stage, retryability, and structured diagnostics as optional additive fields.
- Retain `force` as a compatibility alias but define it as `force_recompute`; document the semantics explicitly.
- Continue supporting `persist_db` during migration, while production release candidates always require persistence.

### Pinecone and retrieval compatibility

- Preserve every metadata key currently consumed by retrieval.
- New provenance fields are additive.
- Continue storing legacy `chapter`, `section`, `article`, `paragraph`, `page_start`, and `page_end` values derived from the richer hierarchy.
- Keep release namespace selection and activation behavior unchanged.
- Do not modify retrieval code during the architecture or initial ingestion migration phases.

### Artifact compatibility

- Add a read-only v2 compatibility reader that converts existing artifacts into the normalized model where possible.
- Mark fields that cannot be reconstructed—such as exact source spans—as unavailable; do not fabricate them.
- Never rewrite checksums or metadata inside existing v2 builds.

### Database compatibility

- Apply nullable/additive columns first.
- Dual-write new and legacy fields for v3 builds.
- Backfill only deterministic fields derivable from existing records.
- Leave unavailable provenance null and require a true v3 re-ingestion before a document is declared v3-complete.
- Retain the previous active release until the v3 corpus is approved and the rollback period ends.

## Testing strategy

### Characterization tests

Before behavior changes, freeze the current active pipeline's observable output for representative documents. These tests make migration differences explicit rather than accidental.

### Unit tests by stage

- **Sources/validation:** malformed, truncated, encrypted, oversized, zero-page, wrong-media, checksum mismatch, and duplicate PDFs.
- **Extraction:** born-digital, rotated, two-column, mixed-column, table-heavy, scanned, mixed scanned/text, and corrupted-character pages.
- **Cleaning:** headers, footers, page titles/numbers, whitespace, Unicode, dehyphenation, line reflow, duplicate blocks, boilerplate, and exact source-map preservation.
- **Structure:** all target legal node types, inline markers, OCR aliases, numbering gaps/duplicates, invalid nesting, page transitions, explanations, and attachments.
- **Chunking:** Pasal/Ayat boundaries, oversized leaves, continuations, sibling/parent links, BGE hard limits, no forbidden cross-Pasal merge, and stable IDs.
- **Metadata:** complete required fields, canonical serialization, source spans, deterministic hashes, and legacy Pinecone mapping.
- **Deduplication:** exact same-version duplicates, cross-version duplicates, aliases, near duplicates, and non-removal of distinct legal provisions.
- **Embedding:** batching, retry classification, timeouts, rate limits, malformed provider responses, wrong dimensions, zero/non-finite vectors, sparse requirements, and checkpoints.
- **Indexing:** partial upserts, missing acknowledgements, wrong metadata, missing IDs, count mismatch, verification, failed namespace cleanup, and manifest determinism.
- **Evaluation:** consistent blocking/advisory/waiver policy and reviewer disposition rules.

### Property and determinism tests

- The same complete inputs produce identical IDs, chunks, metadata, and artifact checksums.
- A change to bytes, canonical metadata, stage configuration, schema version, code revision, or vector space changes the appropriate identity.
- Every normalized span maps to valid source ranges.
- Chunk source spans remain ordered, non-empty, and within source page bounds.
- No final retrieval text exceeds the real embedding tokenizer maximum.

### Integration tests

- CLI and API paths produce the same build identity and artifacts.
- Celery retries and resumes the correct stage against PostgreSQL.
- OCRmyPDF/Tesseract selectively process only requested pages.
- Pinned BGE-M3 produces valid 1,024-dimensional dense and native sparse vectors.
- Pinecone staging receives and returns every expected vector and checksum.
- Governance blocks unverified sources/builds and allows only fully verified release candidates.

### Migration tests

- Upgrade a database containing current v2 documents, builds, chunks, embeddings, jobs, and releases.
- Confirm existing APIs and active release retrieval continue to work.
- Confirm v2 artifacts remain readable and immutable.
- Confirm v3 dual writes populate both normalized and legacy fields.
- Confirm downgrade/rollback policy for the additive migration is documented and tested where data loss is not involved.

### Golden ingestion corpus

Maintain a small source-verified fixture corpus containing:

- a normal born-digital regulation;
- a two-column page;
- a table or attachment;
- a scanned page;
- a mixed OCR/text document;
- legal explanations and attachments;
- malformed and encrypted negative fixtures.

Expected outputs include page dispositions, selected text spans, legal hierarchy, chunk boundaries, provenance, and citations. Full external documents should not be copied into snapshots when compact synthetic or licensed excerpts are sufficient.

## Publish acceptance gates

A v3 build is eligible for publication only when:

1. Every source page has a final disposition.
2. No substantive page remains blocked or undispositioned.
3. Every accepted chunk maps to exact source spans.
4. Every required metadata field is present and valid.
5. Every final retrieval text fits the pinned embedding tokenizer limit.
6. No undispositioned exact duplicate source version or chunk remains.
7. Embedded count equals accepted chunk count.
8. Every vector matches the release vector space and passes numeric validation.
9. Pinecone expected, acknowledged, stored, and verified counts agree.
10. Expected vector IDs and metadata checksums match the index manifest.
11. No blocking extraction, structure, provenance, embedding, or index diagnostic remains.
12. Any allowed waiver has reviewer identity, evidence, scope, and expiration/review context.
13. Source verification, legal review, build approval, and retrieval regression thresholds pass.

## Staged implementation roadmap

### Stage 1 — Contracts and characterization

- Add normalized domain contracts, enums, canonical serialization, diagnostic codes, and protocol interfaces.
- Add characterization tests around the active v2 pipeline.
- Make no production behavior or database changes.

**Exit:** Models and interface contracts are accepted; current behavior is reproducibly captured.

### Stage 2 — Identity, runs, and additive persistence

- Introduce document/version/build/run separation and complete build fingerprints.
- Add the first additive migration and v3 artifact manifest.
- Preserve API responses and dual-write legacy state.

**Exit:** Metadata/code/config changes cannot reuse stale builds, and forced runs have correct semantics.

### Stage 3 — Page fidelity

- Implement typed PDF validation, layout blocks, table extraction, selective OCR, normalized pages, and source maps.
- Generate v3 page artifacts in shadow mode for the current corpus.

**Exit:** Every page is dispositioned and source mapping passes the golden corpus.

### Stage 4 — Legal structure and chunking

- Implement the normalized Indonesian legal tree and structure validator.
- Add tokenizer-enforced legal chunking and deterministic provenance metadata.
- Add `legal_nodes` and extended chunk persistence.

**Exit:** Complete legal paths and exact source spans are available for every v3 chunk.

### Stage 5 — Deduplication and embeddings

- Enforce explicit document/version duplicate policy.
- Add exact chunk deduplication and near-duplicate review reports.
- Add resilient embedding batches, vector-space checks, checkpoints, and telemetry.

**Exit:** Accepted chunks and valid embedding records reconcile exactly.

### Stage 6 — Verified indexing and evaluation

- Add staging-only indexing, complete index manifests, read-back reconciliation, and cleanup.
- Replace inconsistent gate evaluation with one shared policy.
- Run deterministic ingestion and retrieval probes.

**Exit:** An incomplete or inconsistent namespace cannot transition to validated.

### Stage 7 — Controlled corpus cutover

- Build v3 shadow candidates for the complete corpus.
- Compare v2 and v3 extraction, structure, chunks, retrieval, and citations.
- Obtain source/legal/build approvals.
- Activate one immutable v3 release while retaining the previous release for rollback.

**Exit:** The active knowledge base uses approved v3 builds with no retrieval-code changes.

### Stage 8 — Consolidation

- Port only proven capabilities from `app.services.rag` into the authoritative modules.
- Remove obsolete compatibility writes and superseded ingestion code after the rollback window and full corpus migration.
- Keep historical artifacts and release records immutable.

**Exit:** One authoritative ingestion implementation remains, with documented ownership and operational runbooks.

## Operational metrics

Record by stage, document, version, build, and run:

- input bytes and source pages;
- pages by extraction mode/disposition;
- characters/words before and after OCR/cleaning;
- OCR quality delta and failures;
- tables and table extraction confidence;
- legal nodes by type, sequence gaps, and parser confidence;
- chunks, tokenizer percentiles, overlap ratio, and duplicate rates;
- required metadata coverage;
- embedding batches, retries, latency, token volume, failures, and cost estimate;
- expected/acknowledged/verified indexed vectors;
- stage and total duration;
- blocking/advisory diagnostic counts;
- ingestion and retrieval regression results.

Logs must be structured and keyed by `run_id`, `build_id`, `version_id`, and `document_id`. Sensitive provider details and credentials must never be included.

## Assumptions

- `app.services.ingestion` remains the authoritative namespace.
- PostgreSQL remains the system of record.
- Pinecone remains the production vector database.
- Celery/Redis is mandatory in production; FastAPI background execution is development-only.
- BGE-M3 remains pinned at 1,024 dimensions until a separately evaluated vector-space migration.
- PDF is the only enabled input format for the first target implementation.
- Existing administrator governance and release activation remain authoritative.
- Retrieval code and current consumed Pinecone metadata fields remain unchanged during the migration.
- This document is architectural guidance only; it does not itself authorize production changes.
